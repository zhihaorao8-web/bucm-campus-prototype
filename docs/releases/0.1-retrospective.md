# 0.1发布复盘与下次发布检查

日期：2026-11-09。适用于Flutter Android工程`mobile/`。

## 结论

这次发布反复重试，主要是首次把本机工程放进干净的Windows CI后，环境差异没有提前检查；另有release插件注册与R8问题在打包时才暴露。最后一轮不是构建无法进行，而是首次安装工具、编译和打包较慢。维护过程中取得实时日志偏晚、反复查询状态，也延长了用户等待。

最终发布源码为`06fcd928826d2361d9c0f15c4012fa309fbf7de9`；[成功构建](https://github.com/zhihaorao8-web/bucm-campus-prototype/actions/runs/42624590207)耗时16分26秒，静态分析、合成测试、release构建及产物上传均通过。[v0.1](https://github.com/zhihaorao8-web/bucm-campus-prototype/releases/tag/v0.1)为开发签名预发布。

## 实际问题与处理

| 问题 | 已确认原因与证据 | 本次修复 | 下次防范 |
|---|---|---|---|
| Windows无法检出Flutter SDK | [首轮CI](https://github.com/zhihaorao8-web/bucm-campus-prototype/actions/runs/42620541103)出现`Filename too long` | 克隆SDK时启用`core.longpaths=true`，保持SDK版本与提交SHA锁定 | 新runner先验证SDK检出，不能用本机已有SDK代替干净环境检查 |
| pub依赖完整性校验失败 | [第二轮CI](https://github.com/zhihaorao8-web/bucm-campus-prototype/actions/runs/42620919458)下载`flutter_inappwebview_ios 1.1.2`时出现`wrong content-hash`；锁文件SHA与官方元数据一致 | CI使用pub.dev，只替换锁文件的源地址，不改版本或SHA，保留`--enforce-lockfile` | 海外runner使用官方源；校验不符先核对源与下载内容，禁止删除SHA或放宽校验。具体为何返回错误文件未独立查明，不归因于库代码 |
| Kotlin release编译失败 | [第三轮CI](https://github.com/zhihaorao8-web/bucm-campus-prototype/actions/runs/42621978532)明确报`this and base files have different roots`：pub缓存位于C盘、工程位于D盘 | `PUB_CACHE`放到`${{ github.workspace }}\build\pub-cache` | Windows CI确保依赖源码与项目同盘；本机预热缓存不能代替检查runner路径 |
| 本地release插件类缺失 | 使用`--no-pub`时，生成的注册表残留开发测试插件，release类路径中没有对应类 | 使用普通`flutter build apk --release`重新生成正确注册表 | 不手改生成文件、不将测试依赖移入生产；不要并发运行会刷新注册表的Flutter命令与release构建 |
| R8缺类与反射风险 | release压缩暴露HSSF反射、Log4j服务发现及未使用的桌面/OSGi类；debug通过不能证明压缩包可解析XLS | 精确保留反射边界、限定缺类规则，并运行隔离的release合成XLS测试 | 保持R8启用，解析依赖/规则变更后验证压缩包实际读取；测试包不覆盖用户应用，测试后重建正常包名APK |
| 测试运行器跨APK类缺失 | release测试目标压缩了运行器共用的Kotlin/Tracing类，造成测试启动错误 | 仅在隔离测试目标保留共享运行时；测试APK规则独立 | 区分测试框架失败与业务解析失败；不把测试专用保留规则带入发布包 |
| Git推送中断 | 本机到github.com连续出现连接超时、重置；GitHub API可访问 | 使用官方Git Data API同步现有对象，逐条核对提交哈希，仅快进更新分支 | 先读服务器分支SHA判断是否成功，再有限重试。API作为备用时必须保持Git对象哈希及历史；不能强推或关闭TLS。凭据只在内存，不写入脚本/日志 |

CI还调整为使用官方Gradle仓库，本机仍保留镜像。这是针对runner网络环境的预防措施；没有证据证明国内Maven镜像是第三轮失败的根因，已确认的直接原因是Kotlin跨盘缓存。

## 为什么最后一轮看起来没有进度

最后一轮的GitHub网页实时日志显示（北京时间）：

- 21:22:45进入Android release构建。
- 21:26:58完成NDK解压。
- 21:30:21完成CMake安装。
- 21:31:35仍有Java编译输出，内容是警告，并非失败。
- 任务最终成功，整轮耗时16分26秒。现有日志不足以把剩余耗时精确归给R8、网络或其他子任务，不据此宣称死锁或某个具体任务卡住。

CLI/API能读取步骤状态，但运行期间下载完整日志返回404；网页仍能展开实时日志。此前仅重复轮询状态，没有及时换到网页查日志，是本次排查方式的问题。`in_progress`只能证明runner尚未结束，不能证明具体子任务健康；日志下载404也不能证明构建失败。

## 下次发布的固定顺序

1. **先核对现状**：读取工作区、远程分支、发布要求及版本来源。确认用户是否暂停提交；只处理本次范围，不为发布混入其他功能。
2. **先检查环境**：固定Flutter SHA、Gradle校验值及依赖锁；Windows启用长路径，pub源码与项目同盘；CI选择官方源。涉及工具链调整时先验证干净runner，不等打标签后才检查。
3. **先做本地release验证**：运行对应合成检查和普通release构建。检查正常包名、根Manifest版本、非debug状态、签名、许可资产、ZIP完整性及测试数据未入包；必要时在隔离模拟器验证压缩后的解析和启动。
4. **检查后同步，再等待指定提交CI**：按精确SHA核对，不能把旧提交成功当成本次成功。新修复推送会取消旧构建，避免没有日志依据便连续改配置、重启冷构建。
5. **等待要有证据**：发布构建使用详细日志，例如`flutter build apk --release --verbose`；流水线修改时应保留失败诊断日志并核对退出码，不能用管道掩盖失败。当前工作流尚未自动保存详细打包日志，这是后续可实施项，不写成已完成。
6. **发现长时间没有新日志时主动诊断**：超过约5分钟没有输出是调查触发条件，不是失败判据。查看网页实时日志的最新时间与内容；区分下载、工具安装、编译、压缩和上传。API日志不可用则使用网页，不持续只查`in_progress`，不凭耗时猜根因。
7. **汇报结果而非轮询次数**：说明已确认的阶段、最后日志时间、已知错误和下一项检查；不反复承诺“马上完成”。没有新证据时明确说仍待结果，不声称未出错就等于正常。
8. **成功后才发布**：在通过CI的提交上新增标签；保留旧标签。上传经本机验签的APK和校验文件，核对GitHub返回的资产摘要与大小，明确预发布及签名性质。发布记录的后续文档提交不能移动发布标签。

- 按锁定版本与缓存键评估Flutter、pub、Gradle、NDK/CMake缓存；先验证正确性再比较耗时，不承诺缓存一定命中或构建一定在某时限内完成。
