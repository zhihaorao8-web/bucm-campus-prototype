# 长期项目管理与开发流程

生效：2026-11-16。用户明确要求将本轮优化方法用于后续开发并严格遵守。本文适用于所有后续功能、UI、修复、重构和文档工作，不限于A–F工程优化；[MAINTENANCE_PLAN](MAINTENANCE_PLAN.md)只保留该轮实施台账。后续用户明确确认的范围与决定优先，旧提示词、旧接续或一次性发布授权不能扩大当前任务。

## 开工前必须核对

1. 阅读[生效需求](PROJECT_BRIEF.md)、[当前进度](DEVELOPMENT_PLAN.md)、[验证证据](STATUS.md)及[AGENTS](../AGENTS.md)；UI同时读[DESIGN](../DESIGN.md)，定位计算/组件先查[架构与复用索引](ARCHITECTURE.md)。
2. 检查工作分支、HEAD、工作区及已有实现，确认哪些成果已实现、已检查、已推送或仍待审核。保留用户其他未提交改动，不覆盖、混入或重做已有成果。
3. 把任务拆成可独立验证和审核的阶段，写入DEVELOPMENT_PLAN：范围、交付物、受影响模块、最小检查、必要人工验证与停止点。小型文档/修复可以只有一个阶段，不为套流程扩大任务。
4. 新阶段、新模块或影响范围/认证/验收的实质变更，先给范围和可复核结果，取得确认后实施。已确认阶段内常规实现、修复和验证继续执行，不重复索取确认；歧义一次只问一个问题。

## T3 Code 多 agent 协作

Codex 对整个工作分支负责。用户确认阶段后，Codex 可直接将其中的页面设计委派给 Antigravity。纯业务、平台和维护任务由 Codex 处理。

| 负责人 | 交付与边界 |
|---|---|
| Antigravity · 页面设计 | 按[设计规范](../DESIGN.md)给出页面布局、组件复用、各状态的展示及交互。设计任务默认回传方案。任务包含 UI 实现时，可修改派单中列出的 Flutter 组件、视觉参数及对应 widget 测试，通过约定的状态和回调连接业务。 |
| Codex · 业务与集成 | 负责 Riverpod 业务状态、领域逻辑、数据存储、学校接口、认证、WebView、Android 桥接与共享 Java 核心。先按[架构索引](ARCHITECTURE.md)给出可用的状态、动作与失败语义。现有页面中混合的业务逻辑也归 Codex，例如课堂页的认证恢复与播放权限检查。 |
| Codex · 最终技术审核 | 对照阶段验收标准审阅方案或完整差异，核对真实调用入口、依赖方向、敏感数据和异常路径；在集成后的工作分支复核受影响的检查与视觉证据。Codex 更新进度与证据、按独立分项提交推送，然后交用户做阶段审核。 |

**开场选模。** 新任务从 Codex 主线程开始，页面设计由 Codex 按已确认的任务范围委派给 Antigravity。每个新对话开场确认 Codex 主模型、Antigravity 设计模型及相应思考程度，首条消息已指定的选项直接采用，只询问缺失项。无需设计时，用户可选择暂不启用 Antigravity。同一对话沿用已确认的选择，用户可随时调整。技能元数据中的示例模型不覆盖用户选择。

### 主线程模型切换与交接

1. **原模型结束当前回合。** 先回读线程配置，区分本回合使用的模型和下一回合的目标配置。跨提供方切换被活动回合拦截时，原模型在同一线程留下接续记录后结束当前回合。记录包含用户已确认的阶段、授权范围和待审核事项，工作分支、基线 SHA 与已有未提交改动，已完成项、验证证据、仍在运行的任务或阻塞，以及下一步。使用可回读的结果和文件位置，省略凭据及真实学校数据。
2. **切换后再发起接续。** 回合结束后，由能在回合外操作该线程的一方按用户选定的提供方、模型和思考程度修改配置，并回读确认。若当前只有活动回合内的工具可用，原模型在结束时说明当前仍用哪个模型，并请用户在 T3 Code 界面切换后从同一线程继续。回读不一致或切换失败时，保留接续记录，说明阻塞，等配置确认后再发起接续回合。
3. **核对实际接手。** 查下一回合的提供方与模型，有 `executedModel` 时也核对实际执行值。接手模型简短确认已获授权的范围、当前基线、已有成果和下一步，涉及文件修改时先核对工作区。配置已更新或上下文传输标记为 `consumed` 只记录各自状态，接手要以新回合的运行记录和对任务状态的核对为准。原阶段若仅获准出方案或仍待审核，接手继续遵守该范围和停止点。

### 技能与工具按任务选择

Codex 在派单前核对当前会话的技能目录和可调用工具，Antigravity 在开始时回传本任务适用技能及所需工具的可用状态。两方分别读取适用的 `SKILL.md`，以用户确认的范围、项目规范和现有 Flutter 实现决定采用哪些步骤。技能中的框架、依赖、预览及自动修复建议须核对本项目环境和修改范围。每阶段选一个主导技能，辅助技能按具体问题加载。自动修复和生成后审阅完整差异，将修改限定在任务范围内。

| 工作内容 | 负责人及可用能力的使用方式 | 交接要求 |
|---|---|---|
| Flutter 布局、窄屏与大字适配 | Antigravity 优先选 Flutter 插件中的 `flutter-build-responsive-layout`、`flutter-fix-layout-issues`，按父约束和首个布局异常定位问题 | 给出复用组件、约束来源、适配状态和实际观察结果 |
| widget 交互与局部验证 | Antigravity 按任务选 `flutter-add-widget-test`、`dart-run-static-analysis`，复用 `mobile/test` 和分层检查入口 | 回传执行命令、工作目录、退出码和覆盖状态，由 Codex 集成复核 |
| Flutter 运行时诊断 | Antigravity 在 Dart MCP 已连接合成数据 debug 应用时，可用 `widget_inspector`、`get_runtime_errors`、热重载等能力 | 记录应用基线及连接状态，运行时操作与构建由约定的一方串行执行 |
| 组件预览 | Antigravity 可选 `flutter-add-widget-preview`，先核对锁定 SDK、插件和组件依赖是否支持 | 预览记录注明尺寸、字号、主题和替身，Web 预览涉及原生插件时须明确缺口，Android 真实入口继续验证 |
| 视觉审阅与动效 | 两方可参考 `frontend-stack` 的按阶段选技能原则，按需参考 `impeccable`、`ui-ux-pro-max`、`emil-design-eng` | Flutter 参数与验收采用 DESIGN 和公共令牌，Web 专用 CSS、字体、布局规则按适用性取舍 |
| Pen（pen.dev）前端设计与客户端评审 | Antigravity 优先通过 `pencil` MCP 在 `design/bucm-campus.pen` 完成视觉令牌、组件复用与页面设计，并在 Pen 桌面客户端向用户呈现与审核，通过后再落 Flutter 代码 | 仅使用合成示例数据；`.pen` 为加密设计文件，仅经 `pencil` MCP 读写，不直接以文本读取/检索 |
| 图标素材 | Codex 可通过 IconMCP 检索与获取，按[图标流程](ICON_SYSTEM.md)登记并打包离线资产，Antigravity 优先复用 `AppIcons` | 缺少图标时回传语义及尺寸，由素材获取方交付业务别名、来源和许可 |
| 学校协议、平台与异常路径 | Codex 复用现有代码、具名检查和必要的 REA、抓取或设备工具诊断，按实际问题选工具 | 接口、认证、账号隔离和平台行为的调整由 Codex 审核，学校验证遵守本人授权会话规则 |
| 大日志与上下文 | Antigravity 可选 context-mode 提炼日志，两方均保留完整本地日志和退出码 | 回传原始日志位置、关键错误与结论依据，摘要支持追溯 |

安装目录、MCP 配置、工具定义、当前会话可调用、实际执行成功分别记载。父 agent 的工具清单仅说明父会话能力，子 agent 自行确认实际暴露的工具和连接。按任务做最小只读验证，启动应用、改依赖、生成原型等操作随已确认任务执行。工具失败时保留错误和证据，用项目已有命令完成仍可执行的检查，必要项缺失则注明阻塞。插件安装、全局配置或工具链升级须属于用户授权范围。

### 派单与执行

**派单。** Codex 在当前线程首次委派前用 `orchestrator_capabilities` 核对提供方和模型，再通过 `delegate_task` 显式传入 `target.providerInstanceId: antigravity`、用户选定的 `target.model` 及能力目录支持的 `target.options`。思考程度须按该模型实际支持的选项传递，缺失或不支持时如实说明并确认处理方式。模型不可用时，请用户选择可用型号。提供方不可用或任务失败时，如实记录阻塞并继续独立的业务工作；更换设计代理由用户决定。子任务只获得派单内容，须写全上下文。可直接填写以下模板：

```text
阶段与任务：〈已确认的阶段、页面入口、用户要完成的操作〉
交付：〈只读设计方案 / 设计及 Flutter 实现〉
基线与范围：〈工作分支、基线 SHA、已有未提交改动、允许修改的文件、须复用的组件〉
模型与能力：〈提供方、模型、思考选项、适用技能、所需工具及待验证连接〉
执行归属：〈共享目录或隔离工作树、文件写入人、测试/构建/设备操作人〉
接口与样本：〈状态来源、操作回调、错误/取消语义、合成示例〉
验收：〈适用的 DESIGN 条目、最小测试或预览、需人工核对的状态〉
回传：〈方案或改动文件、实际采用的技能/工具、命令与退出码、日志/合成视觉证据、未验证项及接口问题〉
```

**并行与交接。** 共享工作区中，同一文件同时只由一方写入。页面与业务同文件时，先交接设计，由 Codex 串行集成；需要并行改代码时先划清文件和接口。共享目录会包含已有未提交改动，须在任务单列明保护范围。使用 `isolation: worktree` 时核对基线提交及必需依赖，父目录未提交文件须另行明确传递。Codex 审阅差异后在集成分支接入，核对接口和过期基线。涉及接口缺口时，Antigravity 回传所需状态或动作，Codex 确认后实现。子任务使用合成数据，派单、预览和回传均不得包含真实课程、学校会话、凭据、设备标识或密钥。子 agent 将结果交回 Codex，不自行推送、合入、发版或进入下一阶段。同一 Flutter 工作目录的依赖准备、生成、构建与同一设备上的安装、热重载、状态修改串行执行，归属写入派单。

委派后的等待、恢复和取消遵循 T3 返回的 `next`。任务失败先核对错误，恢复时明确已完成部分与仍需交付内容。废弃或替换运行中的任务先取消，新的独立复核使用新的 `delegate_task`。小型审阅问题由 Codex 直接修复并定向验证。

**验收。** Codex 按[分层测试](TESTING.md)选择受影响检查。设计稿按设计规范审阅；实现后的页面按同一规范核对真实入口、浅深色、窄屏大字、无障碍降级及适用的加载、空、错误或取消状态。分别记录设计审阅、合成测试、设备观察与用户验收。

**Pen 设计媒介。** 已确认阶段涉及前端页面设计或视觉改版时，优先通过 `pencil` MCP 在 [bucm-campus.pen](../design/bucm-campus.pen) 完成设计并在 Pen 桌面客户端向用户呈现与审核，通过后再落 Flutter 实现，详见[设计规范 — Pen（pen.dev）设计媒介与同步规范](../DESIGN.md#penpen-dev设计媒介与同步规范)。

**Stitch 辅助原型。** 已确认阶段涉及新页面或较大视觉改版时，Antigravity 可按[设计规范 — Stitch 辅助设计与原型边界](../DESIGN.md#stitch-辅助设计与原型边界)在编码前选用 Stitch 做合成数据视觉比稿；Stitch 产出仅作原型参考，本地 `.stitch/` 产物不提交，不得替代 Flutter 组件复用、Codex 技术审核与分阶段验收。

## 每个分项的固定顺序

**核对已有实现 → 确定复用点与验收 → 修改 → 分层检查 → 更新证据/进度 → 仅暂存本项 → 提交并普通推送。**

- 每个独立功能/UI分项完成相应检查后立即提交推送，再开展下一分项，不把多项已完成修改积攒到阶段末。文档变更也须检查并按职责同步。
- 提交或推送失败，保留改动/已有提交，报告原因与未同步状态；不得关闭校验、强推、重写历史或把本地提交说成已推送。
- 阶段完成必须停止：汇报改动、检查/跳过项、实际构建与样本范围、提交/推送状态、未完成项及下一阶段范围；用户审核通过后再推进。写完代码、CI通过或推送成功均不能代替用户审核。
- 工作中出现新故障或范围变化，先定位证据和影响，再调整当前计划；旧成功结果不能覆盖新失败，也不能据此恢复已撤销的路线。

## 复用与配置维护

| 内容 | 必须遵循的入口与做法 |
|---|---|
| 交互、视觉与组件 | 按DESIGN的组件/状态/验收表选用；颜色/间距/尺寸/动效读mobile/lib/design，材质降级复用AppVisualPolicy。新变体先扩公共组件和规范，不在页面另写一套 |
| 业务参数、路径与标识 | 先查mobile/lib/config；公开入口、容量、超时、文件名、资源/通道/开关按职责集中。文件名/schema/持久化键及跨语言协议是兼容边界，不能借整理改语义或合并安全白名单 |
| 计算、处理与流程 | 先检索ARCHITECTURE和源码；复用领域计算、收集器、协调器与仓库。新增公共能力登记职责、调用入口、输入输出、失败/取消行为和验证入口，避免再实现相同算法 |
| 存储与平台 | 复用原子写入和各仓库的队列/备份/revision；页面不复制持久化或账号隔离策略。共享维护源按prepare复制，不编辑生成副本 |
| 冗余清理 | 同时查调用、构建/复制、资产、测试和文档引用；先迁移有效断言/规则再删旧方案。目录名像research或legacy不能作为删除依据，不整目录删除共享核心 |

## 分层测试与复用调试

日常只执行与改动相应的检查，准确范围、命令、报告和扩展条件统一见[TESTING](TESTING.md)。

| 变更/目的 | 默认选择 |
|---|---|
| 纯文档 | --module docs，核对描述与代码；不因此运行应用全量或构建APK |
| 单模块实现/修复 | 对应--module或具体相关测试，Dart改动补静态分析；解析/桥接运行对应合成检查 |
| 经常排查的链路 | 复用--flow具名场景；新增场景优先扩现有计划/Runner/报告，不复制第二套执行器 |
| 公共接口/跨模块/不确定影响 | 先--changed --dry-run复核依赖选择，再执行受影响集合；未知变更保守扩大，新增/删除测试同步登记 |
| 发布候选/广泛集成 | --all并补所需Android/R8/媒体和运行时检查；全量宿主也不等于设备/学校验收 |

不在每次小改后重复全量，不为已通过且无新变化/失败/疑点的项目反复扩大检查。失败先看最新日志、时间戳和退出码，再定向修复/复跑；不能凭耗时盲目重启。真实学校只在本人授权会话手动验证，自动检查使用合成数据，不主动清除本人数据制造故障。

## 文档与证据分工

- PROJECT_BRIEF只记录生效范围；DEVELOPMENT_PLAN只维护当前阶段/待办/审核；STATUS记录实际验证证据。DESIGN管组件标准，ARCHITECTURE管复用职责，课堂/播放器专项管协议与实现边界；不在每个入口复制同一套规则和流水账。
- 行为、公共接口、配置或测试入口改变时，同步所属文档；错误或过期内容删除/修正，不仅追加一段相反说明。有效需求来源、协作规则、组件标准、许可和唯一历史证据保留，失效过程用Git追溯，不反复复制归档。
- 明确区分：已实现、静态/合成检查通过、设备/模拟器通过、真实学校样本通过、完整学期/课时/跨天目标通过、已提交/推送、用户审核通过、已合入、已发布。跳过/未运行/阻塞逐项如实记录，不互相替代。
- 验证记录至少包括对象/范围、命令或方法、结果及缺口、相关源码SHA；构建/设备样本另注明模式、版本、APK摘要及观察条件。旧包、旧CI或准备成功不能作为新提交/持续播放/完整验收的证据；规范、模板和远端生效状态分别记录。

## 分支、构建与发布

main保持经审核的稳定主线，日常用独立codex/分支；角色与CI分工以[VERSIONING](VERSIONING.md)为准。普通工作分支/PR按变更检查，集成/候选和显式预览各司其职，不为每次推送默认打包。

构建/发版复用[双包流程与核验工具](BUILD_VARIANTS.md)，在同一明确源码上顺序构建并核对实际模式、版本、签名、资源/许可和摘要；隔离测试后重建正常包名。发布必须有精确候选CI与必要实测证据，不能拿预览、旧提交或一次例外代替。

提交推送不等于合入或发布；main合入、版本/标签/Release、远端保护设置和签名迁移按用户对应授权执行。阶段审核不自动授予这些动作，未生效的远端设置不得写成已配置。认证、TLS、数据保护和未开放模块边界始终遵守AGENTS与PROJECT_BRIEF。
