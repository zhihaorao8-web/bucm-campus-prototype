# 版本与协作规范

2026-11-12新增长期发布要求：后续GitHub新发布同时提供debug测试包（内置测试诊断等功能）和正常release使用包。两包的同源版本、签名、独立验收与附件规则见[双包规范](BUILD_VARIANTS.md)；实验开关与诊断独立，正常包不采集测试诊断。此要求不修改既有标签/附件，也不等于本轮发布授权。

- `main`保存已经检查的进度。日常改动使用`fix/...`、`feat/...`或`docs/...`分支，通过PR说明变更和验证结果后合入。
- 提交使用`fix:`、`feat:`、`docs:`、`test:`、`chore:`等前缀，一个提交围绕一个目的。
- 每完成一项独立的功能性修改或UI修改，运行对应检查后立即提交并推送当前工作分支，再开始下一项；不要积攒多项修改后统一同步。仅暂存本项相关文件，不混入其他未提交工作或个人数据。
- 推送失败时保留本地提交，报告原因和未同步状态；不强制推送、不自动合并main。同步本身不是发布，不自动增加应用版本或创建标签。
- `AndroidManifest.xml`是应用版本唯一来源：`versionName`按用户指定，可使用`0.x`或`0.x.y`；`versionCode`每次可安装发布严格递增。界面从包信息读取，不再写死版本字符串。用户最新指定`0.25`，内部code递增为9；Flutter pubspec规范化为`0.25.0+9`，Android显示和发布标签使用`0.25`/`v0.25`。此前`0.1`/code 7、`0.2`/code 8发布记录保留。
- 每次发布更新`CHANGELOG.md`和`docs/STATUS.md`，保留真实验证边界。
- 发布标签使用`v`加Android版本名。已有`v0.1.4`、`v0.1.5`不移动、不覆盖；此前Flutter版`v0.1`、`v0.2`保留，本次新增`v0.25`，均不重写旧标签。
- 当前是研究原型，GitHub Release标记为Pre-release。不得把验证版标作学校官方产品或稳定生产版。
- `v0.1.4`是首个导入Git的验证基线；更早本地迭代只作文字记录，不伪造提交历史。
- 不把真实个人数据或签名密钥放入任何分支和Git历史。误提交时先停止推送并评估撤销/凭据失效方案，而非仅在后续提交删除。
- CI生成临时签名APK；发布APK若需覆盖既有真机安装，应在可信本机使用原开发签名构建。生产签名方案尚未建立。

当前发布目标：用户于2026-11-12指定`0.26`，Android code递增为10，pubspec为`0.26.0+10`，新标签`v0.26`；上文0.25作为历史记录保留。版本准备、构建、精确提交CI及实际发布状态见STATUS。

发布步骤：运行离线检查和完整构建 → 检查待提交内容 → 提交 → 推送分支 → 等待CI → 创建版本标签与Pre-release。不要通过重写`main`或强制推送修正发布记录。

下次发布前必须复核[0.1发布复盘与检查清单](releases/0.1-retrospective.md)：长路径、依赖源码与项目同盘、官方CI包源、锁文件SHA、插件注册表、R8实际解析及正常包名。构建无新输出时检查网页实时日志，不将日志下载404或`in_progress`当作失败原因；根因未证实时明确标记推测。
